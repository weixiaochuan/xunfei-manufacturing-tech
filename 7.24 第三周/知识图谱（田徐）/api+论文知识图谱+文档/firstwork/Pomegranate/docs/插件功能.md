### 1.2 核心缺失（插件运行时）

当前系统只能 **管理插件元数据**，**不能执行第三方插件代码**。Service 层明确标注：

> "当前 MVP 只实现插件元数据管理：扫描/安装/启用/禁用/卸载/权限授权/设置读写。第三方 JS 插件运行时暂不执行，避免在没有沙箱前扩大安全边界。"

以下 Obsidian 风格核心能力全部缺失：

| # | 功能 | 状态 | 说明 |
|---|------|------|------|
| 1 | **插件 JS 运行时** | ❌ 未实现 | 无法加载和执行 `main.js` |
| 2 | **插件 API (`app` 全局对象)** | ❌ 未实现 | 插件无法调用应用能力 |
| 3 | **插件生命周期** | ❌ 未实现 | 无 `onLoad` / `onUnload` / `activate` / `deactivate` |
| 4 | **插件 UI 注入** | ❌ 未实现 | 不能注入侧边栏视图、命令面板项 |
| 5 | **沙箱安全隔离** | ❌ 未实现 | 无沙箱机制保护用户数据 |
| 6 | **插件设置面板** | ❌ 未实现 | 插件无法提供自定义设置 UI |
| 7 | **CSS/Style 注入** | ❌ 未实现 | 插件声明的 `styles` 属性未使用 |
| 8 | **插件热重载** | ❌ 未实现 | 开发中修改插件需手动重新安装 |
| 9 | **插件市场** | ❌ 未实现 | 无在线浏览/安装插件的渠道 |
| 10 | **插件间依赖** | ❌ 未实现 | 不能声明依赖其他插件 |

## 2. 目标设计（对标 Obsidian）

### 2.1 插件 Manifest 扩展

当前 `plugin.json` 结构：
```json
{
  "id": "my-plugin",
  "name": "我的插件",
  "version": "1.0.0",
  "description": "...",
  "author": "...",
  "main": "main.js",
  "styles": "styles.css",
  "minAppVersion": "1.0.0",
  "permissions": ["notes:read", "notes:write"],
  "contributes": {
    "commands": [
      { "id": "do-something", "title": "执行操作" }
    ],
    "sidebarViews": [
      { "id": "my-view", "title": "我的视图" }
    ],
    "settings": true
  }
}
```

**需扩展字段**：
```json
{
  "dependencies": { "other-plugin": ">=1.0.0" },  // 新增：插件依赖
  "contributes": {
    "ribbonIcons": [                                 // 新增：功能区图标
      { "id": "my-ribbon", "title": "工具", "icon": "star" }
    ],
    "editorExtensions": ["ext1", "ext2"],            // 新增：编辑器扩展
    "statusBarItems": [                              // 新增：状态栏项
      { "id": "my-status", "text": "就绪", "align": "right" }
    ]
  }
}
```

### 2.2 插件 API 设计（`app` 全局对象）

插件通过全局 `app` 对象访问应用能力，对标 Obsidian Plugin API：

```typescript
// 插件获取的 API 对象
interface AppAPI {
  // 工作区
  workspace: {
    getActiveNote(): Note | null;
    getActiveEditor(): Editor | null;
    onActiveNoteChange(cb: (note: Note | null) => void): EventRef;
  };

  // 笔记操作
  notes: {
    get(id: number): Promise<Note>;
    create(input: NoteInput): Promise<Note>;
    update(id: number, input: NoteInput): Promise<Note>;
    delete(id: number): Promise<void>;
    list(query: NoteQuery): Promise<PageResult<Note>>;
    search(keyword: string): Promise<SearchResult[]>;
  };

  // 文件系统（受权限控制）
  vault: {
    readText(path: string): Promise<string>;
    writeText(path: string, content: string): Promise<void>;
    listDir(path: string): Promise<string[]>;
    exists(path: string): Promise<boolean>;
  };

  // 命令注册
  commands: {
    addCommand(command: Command): void;
    removeCommand(id: string): void;
    executeCommand(id: string): void;
  };

  // 设置存储（插件专属）
  settings: {
    get(key: string): Promise<unknown>;
    set(key: string, value: unknown): Promise<void>;
  };

  // 通知
  notices: {
    show(message: string, duration?: number): void;
    error(message: string): void;
  };

  // 生命周期
  metadata: {
    id: string;
    name: string;
    version: string;
    dir: string;       // 插件安装目录（用于读取资源）
  };
}
```

### 2.3 插件生命周期

```
┌─────────────────────────────────────────────────────┐
│  应用启动                                             │
│    ↓                                                 │
│  scan_plugins() 扫描 plugins/ 目录                    │
│    ↓                                                 │
│  对每个 enabled=true 的插件：                          │
│    1. 读取 plugin.json → 校验                           │
│    2. 读取 main.js                                    │
│    3. 构造 AppAPI 实例（只暴露已授权的权限）             │
│    4. 沙箱中执行 main.js                               │
│    5. 调用 plugin.onLoad({ app, metadata })           │
│    ↓                                                 │
│  插件运行中...                                         │
│    ↓                                                 │
│  用户禁用插件 / 应用关闭                                │
│    1. 调用 plugin.onUnload()                           │
│    2. 清理注册的命令/视图/事件监听                        │
│    3. 清理沙箱                                        │
└─────────────────────────────────────────────────────┘
```

**插件脚本约定**（类似 Obsidian）：
```javascript
// main.js — 插件入口
module.exports = {
  onLoad: function(ctx) {
    // ctx.app — AppAPI 实例
    // ctx.metadata — 插件元信息
    ctx.app.commands.addCommand({
      id: "hello",
      name: "打个招呼",
      callback: () => ctx.app.notices.show("Hello!")
    });
  },
  onUnload: function(ctx) {
    // 清理
    ctx.app.commands.removeCommand("hello");
  }
};
```

### 3.2 安全沙箱方案（关键决策）

| 方案 | 描述 | 隔离度 | 开发量 | 性能 | 推荐 |
|------|------|--------|--------|------|------|
| **A. 权限代理（Obsidian 式）** | JS 直接在主线程执行，所有操作通过 AppAPI → Rust Command 代理，权限在 Rust 侧校验 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ **推荐** |
| **B. Web Worker** | 插件跑在 Worker 里，通过 postMessage 通信 | ⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ | 备选 |
| **C. iframe 沙箱** | 插件跑在 sandboxed iframe 里 | ⭐⭐⭐⭐⭐ | ⭐ | ⭐⭐ | 不推荐 |
| **D. QuickJS/Deno 嵌入** | Rust 侧嵌入 JS 引擎执行插件 | ⭐⭐⭐ | ⭐ | ⭐⭐⭐ | 不推荐 |

**选择方案 A（权限代理 + 可控 API）**，理由：

1. **与 Obsidian 模式一致**：Obsidian 同样没有沙箱——插件直接跑在 Electron 主/渲染进程，安全完全靠"能力 API"控制粒度
2. **最低开发成本**：前端已有完整的 `invoke → Command → Service → Database` 链路，只需包装成 `AppAPI` 暴露给插件，无需引入新运行时
3. **最佳兼容性**：插件可以直接使用浏览器 API、操作 DOM（用于注入 UI），不受 Worker/iframe 限制
4. **桌面应用特有安全优势**：用户的插件是手动安装的本机文件，不像浏览器扩展来自商店；Tauri 的 Capabilities 本身是第二层防线

**风险缓解**：
- 所有读写操作走 Rust Command → Service 层权限校验（不在前端做权限判断）
- 文件访问限定在沙箱作用域（`$APPDATA/plugins/<id>/`）
- 网络请求必须声明 `network:request` 权限
- 用户安装插件时显示权限列表、需手动授权

### 3.3 前后端分工

| 职责 | 位置 | 说明 |
|------|------|------|
| 插件元数据 CRUD | Rust (已有) | `database/plugins.rs` |
| 插件扫描/安装/卸载 | Rust (已有) | `services/plugins.rs` |

## 7. 风险与注意事项

| 风险 | 级别 | 缓解措施 |
|------|------|---------|
| 恶意插件读取敏感笔记 | 🔴 高 | AppAPI 不暴露"读取所有笔记内容"的接口；走 Command 层权限校验 |
| 恶意插件删除/破坏文件 | 🔴 高 | 文件操作限定沙箱目录；删除操作需二次确认 |
| 插件 JS 代码注入攻击 | 🟡 中 | 用 IIFE 隔离作用域；禁止 `eval`/`document.write` |
| 插件崩溃影响主应用 | 🟡 中 | 单插件 try-catch 包裹；崩溃不影响其他插件和主应用 |
| 插件性能问题导致卡顿 | 🟡 中 | API 调用频率限制；长耗时操作提示用户 |

## 10. 设计修订 v2（2026-06-06）

> 本章节为方案设计的修订集合，由"方案设计审查"得出。
> 原 §1-§9 保留作为历史。当 §10 与上文冲突时，**以 §10 为准**。
> 本章节仅涉及**设计修订**，不含代码改动。落地需另起任务。

### 10.0 修订背景

审查发现 5 项设计/实现偏差与 6 项中高风险，核心问题：

1. **权限校验位置错误**：文档 §3.2 声明"在 Rust 侧校验"，但实际 `pluginApi.ts:30` 完全在前端做 `hasPermission()`，恶意插件可直接覆盖该函数绕过。
2. **AppAPI 形态不一致**：文档 §2.2 定义在 `ctx.app.commands.addCommand`，实际实现却把 `registerCommand` 挂在 `ctx` 顶层，且 `ctx.app.commands.addCommand` 与 `ctx.registerCommand` 存在两套并存路径。
3. **命令注册表全局共享**：`window.__pluginRegisteredCommands` 单例 Map 被所有插件共写，A 插件可覆盖 B 插件的同名命令；卸载时只清按插件分桶的 `__pluginCmds_<id>`，幽灵命令残留。
4. **样式注入无 scope**：插件 CSS 直接进 `<head>`，可写 `* { display:none }` 破坏整个 UI。
5. **`window.__plugin*` 命名空间污染**：用 `window` 全局对象做注册表，任何脚本可读改。

### 10.1 修订项 R1：权限校验下沉 Rust（🔴 必须）

#### 问题
前端 `hasPermission()` 仅是函数闭包包装，插件 JS 与 AppAPI 同上下文，可绕过：
```js
// 恶意插件：拿到原始 noteApi 引用即可越权
const raw = await import("@/lib/api");
raw.noteApi.list({ page_size: 9999 });
```

#### 新设计：插件令牌 + Rust 侧校验

**架构调整**：
```
插件 JS → AppAPI.notes.list()
            ↓
       invoke("plugin_proxy_notes_list", { pluginToken, ...args })
            ↓
       Rust Command 层：
         1. 校验 pluginToken 有效（防伪造）
         2. 查 plugin_permissions 表，验证该插件是否拥有 notes:read
         3. 通过 → 调 Service 层；不通过 → 返回 PermissionDenied
```

**关键设计点**：

| 点 | 决策 |
|---|---|
| 插件令牌生成 | 应用启动时为每个已激活插件生成 UUID v4，存于 Rust 侧 `Mutex<HashMap<PluginId, Token>>` |
| 令牌注入 | `PluginManager.activatePlugin()` 通过 invoke 向 Rust 申领令牌，构造 AppAPI 时闭包捕获 |
| 令牌生命周期 | 插件停用/重载时调用 `invoke("plugin_revoke_token", { pluginId })` 作废 |
| Command 命名约定 | `plugin_proxy_<domain>_<action>`，例如 `plugin_proxy_notes_list` |
| 权限映射 | 在 Rust 侧建立 `Command → required_permission` 静态表 |

**Rust 侧新增 Command（示意）**：
```
plugin_acquire_token(plugin_id) → String       // 令牌申领
plugin_revoke_token(plugin_id)                  // 令牌作废
plugin_proxy_notes_list(token, query) → ...    // 受控笔记列表
plugin_proxy_notes_get(token, id) → ...
plugin_proxy_notes_create(token, input) → ...
plugin_proxy_notes_update(token, id, input) → ...
plugin_proxy_notes_delete(token, id) → ...
plugin_proxy_settings_get(token, key) → ...
plugin_proxy_settings_set(token, key, value) → ...
```

> 注意：令牌不能防御"恶意插件拿到令牌后调用未授权 API"，**真正的防御点是 Rust Command 内的权限表查询**。令牌的作用是把"哪个插件在调用"这一身份信息**可信地传递到 Rust 侧**（不依赖前端声明）。

**权限错误统一类型**：
```
AppError::PluginPermissionDenied { plugin_id, required_permission }
  → 前端转译为统一的 "权限不足: <perm>" 消息
```

#### 前端职责裁剪
`pluginApi.ts` 的 `hasPermission()` **降级为 UX 提示**（提前给出友好错误），**不再作为安全边界**。真正的安全边界在 Rust。

#### 配套迁移
- 现有 `noteApi.list()` 等直接走 `invoke("list_notes")` 的调用**不变**（用户主操作）；
- 仅插件 AppAPI 内部转向 `invoke("plugin_proxy_*")`。

### 10.2 修订项 R2：AppAPI 形态统一（🔴 必须）

#### 决策
**唯一规范入口为 `ctx.app.*`**。移除 `ctx.registerCommand` / `ctx.registerSidebarItem` / `ctx.registerPanelView` / `ctx.registerSettings` 顶层方法。

#### 修订后的 PluginContext 结构

interface PluginContext {

### 10.3 修订项 R3：命名空间强制前缀（🟡 强烈推荐）

#### 决策
所有插件注册的 ID（命令、侧边栏项、面板视图、设置页签）**自动加 `<pluginId>:` 前缀**。

#### 规则
- 插件代码侧：`app.commands.addCommand({ id: "hello", ... })`
- 注册到全局表时：实际存储为 `cc:hello`（假设 pluginId = `cc`）
- 命令面板显示：分组按插件名，命令文本不显示前缀
- 重复注册：同一插件内 id 重复 → 后注册覆盖 + 告警；跨插件不会冲突
- 卸载清理：按前缀 `<pluginId>:` 批量删

#### 收益
- 彻底消除跨插件命名冲突
- 卸载时只需按前缀过滤，不再依赖 `__pluginCmds_<id>` 全局键

### 10.4 修订项 R4：注册表脱离 window（🟡 强烈推荐）

#### 问题
`window.__pluginCmds_*` / `__pluginSbar_*` / `__pluginViews_*` 暴露在全局，任何脚本可读改，且 HMR/SSR/测试场景容易污染。

#### 新设计

```
PluginManager 内部维护：
  private registry: {
    commands:   Map<string, PluginCommandDef>      // key = "<pluginId>:<id>"
    sidebar:    Map<string, PluginSidebarItemDef>
    panelViews: Map<string, PluginPanelViewDef>
    settingsTabs: Map<string, PluginSettingsTabDef>
  }
```

**对外暴露**：通过 PluginManager 实例方法（`getCommands()`, `subscribeRegistryChange()` 等），React 组件用自定义 Hook 订阅。

**事件机制升级**：用 EventTarget 替代 `window.dispatchEvent`，避免污染 window：
```typescript
class PluginManager extends EventTarget {
  // emit 'registry:changed' 事件
}
```

### 10.5 修订项 R5：CSS 样式 scoping（🟡 强烈推荐）

#### 决策
插件 CSS 注入时**自动加作用域前缀**，限制其影响范围。

#### 方案（二选一）

**方案 A：PostCSS 编译期注入前缀**（推荐）
- 插件 `styles.css` 加载后用 PostCSS 处理，所有选择器加上 `[data-plugin-scope="<id>"]` 前缀
- 插件视图容器加 `data-plugin-scope="<id>"` 属性
- 优点：彻底；缺点：依赖 PostCSS 运行时

**方案 B：注入到 Shadow DOM**
- 插件视图容器为 Shadow Root
- CSS 自然隔离
- 优点：浏览器原生；缺点：插件无法访问主应用的设计令牌 CSS 变量（需穿透）

**决策**：阶段 4 实现时**默认方案 A**，方案 B 留作后续选项。

#### 黑名单兜底
对插件 CSS 做静态校验：
- 禁止 `*` 通配符顶层选择器（如 `* { display:none }`）
- 禁止覆盖 `body / html / #root`
- 违规 → 拒绝注入并告警

### 10.6 修订项 R6：插件事件总线（📋 新增设计）

#### 背景
文档 §2.2 的 `onActiveNoteChange` 与 §10.2 删掉的诸多回调都需要事件机制。

#### 新设计

```typescript
interface PluginEventBus {
  on<K extends keyof PluginEvents>(event: K, handler: (data: PluginEvents[K]) => void): () => void;
  emit<K extends keyof PluginEvents>(event: K, data: PluginEvents[K]): void;
}

interface PluginEvents {
  "workspace:active-note-changed": { noteId: number | null };
  "workspace:editor-saved":        { noteId: number };
  "settings:changed":              { key: string };
  // ... 后续按需扩展
}

// 暴露给插件：app.events.on(...)
```

#### 关键约束
- `on()` 返回 unsubscribe 函数；PluginManager 在 `deactivatePlugin` 时**强制收回**插件持有的所有订阅，防止 GC 泄漏
- 事件名采用 `domain:action` 风格，统一注册于 `PluginEvents` 类型，避免拼写错误

### 10.11 实施任务规格（T1-T11 基线）

> 本节定义 T1-T11 的接口契约与验收标准。落地时严格遵循，避免设计漂移。

#### T1：令牌生命周期 Command

**新增 Rust Command**（`src-tauri/src/commands/plugin_runtime.rs`，新建文件）：

```
plugin_acquire_token(plugin_id: String) → Result<String, String>
  - 校验 plugin_id 存在且 enabled = true 且 status = "installed"
  - 生成 UUID v4，存入 Mutex<HashMap>，覆盖旧令牌
  - 返回令牌字符串

plugin_revoke_token(plugin_id: String) → Result<(), String>
  - 从 HashMap 中移除，幂等
```

**新增 Rust 状态结构**（`src-tauri/src/state.rs`）：

```
pub struct PluginTokenRegistry {
    pub tokens: Mutex<HashMap<String, String>>,  // pluginId → token
}

// AppState 持有 PluginTokenRegistry 实例（与 Database 同层）
```

**注册**：
- `commands/mod.rs` 导出 `plugin_runtime` 模块
- `lib.rs` 的 `generate_handler![]` 注册 `plugin_acquire_token` / `plugin_revoke_token`
- `lib.rs` 的 `setup()` 中 `app.manage(PluginTokenRegistry::default())`

**验收**：
- ✅ 同一 plugin_id 多次 acquire 返回不同令牌（轮换）
- ✅ 未安装/未启用 plugin_id 申领令牌返回错误
- ✅ revoke 后 token 立即失效（在 T2 验证）

#### T2：plugin_proxy_* 受控 Command

**新增 Rust Command 模块**（`src-tauri/src/commands/plugin_proxy.rs`，新建文件）：

| Command | 必需权限 | 委托给 |
|---|---|---|
| `plugin_proxy_notes_list(token, query)` | `notes:read` | `NoteService::list` |
| `plugin_proxy_notes_get(token, id)` | `notes:read` | `NoteService::get` |

| `plugin_proxy_settings_get_all(token)` | （同上） | `PluginService::get_all_settings` |

**统一权限校验流程**（提取为 helper）：

```
fn verify_token_and_permission(
    state: &AppState,
    token: &str,
    required_permission: Option<&str>,
) -> Result<String /* plugin_id */, AppError> {
    // 1. 反查 token → plugin_id（HashMap 反向查找）
    // 2. 如果 required_permission.is_some()，查 plugin_permissions 表
    //    确认该 plugin_id 拥有该权限
    // 3. 任一环节失败 → AppError::PluginPermissionDenied
    // 4. 成功 → 返回 plugin_id（供后续 settings 等按插件隔离的操作使用）
}
```

**新增错误类型**（`src-tauri/src/error.rs`）：

```
AppError::PluginPermissionDenied {
    plugin_id: Option<String>,  // None = 令牌无效
    required_permission: Option<String>,  // None = 仅令牌问题
}
```

**注册**：所有 `plugin_proxy_*` 加入 `generate_handler![]`

**验收**：
- ✅ 无效令牌 → `PluginPermissionDenied { plugin_id: None }`
- ✅ 有效令牌 + 缺权限 → `PluginPermissionDenied { plugin_id: Some, required_permission: Some }`
- ✅ 有效令牌 + 有权限 → 正常返回数据
- ✅ revoke 后立即调用 → 拒绝

#### T3：前端 `pluginApi.ts` 改造

**核心变更**：
- 新增参数：`createAppAPI(pluginId, grantedPermissions, pluginDir, **token**)`
- `hasPermission()` 函数**保留**但**降级用途**：仅做 UX 前置提示（"无权限"友好消息），不再作为安全边界
- 所有 API 方法实际调用从 `noteApi.*` / `backendPluginApi.*` 改为 `invoke("plugin_proxy_*", { token, ... })`

#### T4：前端 `pluginManager.ts` 改造

**核心变更**：

1. **激活流程加令牌申领**：
   ```
   activatePlugin(info):
     ...
     const token = await invoke("plugin_acquire_token", { pluginId: info.id });

     ...
   ```

2. **停用流程加令牌作废**：
   ```

     ...

   ```

   - 删除 `ctx.registerCommand` / `ctx.registerSidebarItem` / `ctx.registerPanelView` / `ctx.registerSettings`

5. **EventTarget 替代 window 事件**：
   - PluginManager `extends EventTarget`
   - `dispatchEvent(new Event('registry:changed'))` 替代 `window.dispatchEvent('plugin:sidebar-changed')`

冻结的契约（**任何破坏性变更需升至 2.0.0**）：

- 现有 method 的参数/返回类型
- 现有事件的 payload 结构
- 现有权限键的语义
- 现有错误的字段名
