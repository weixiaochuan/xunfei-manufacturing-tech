# 一、我们这东西到底做得怎么样？

## 1.1 说实话：不错，但没有你想的那么好

**真正做扎实的部分**：
- **题库的"干净"程度** —— 这是我最有底气的地方。982 道题，每一道都能追溯来源（哪张卷子、哪一页、哪个知识点）。没有标准答案的题**一道都没给学生**。这个"宁可少，不可错"的原则，从头到尾没破过。
- **采分点批改** —— 这是真的按老师原卷的评分标准来的，不是"对答案"。
- **双轨制**（学生练习 / 教师出题素材）—— 35 道没答案的真题被隔离在教师端，学生看不到。

**看着好、其实虚的部分**：
- **自适应推题** —— IRT 模型是真的，但**难度值是我估出来的，不是算出来的**。没有真实学生数据，这个模型就是个空架子。你现在看到的"推荐"，本质上是**按题型和分值猜的**。这是最大的水分。
- **趁热打铁** —— 逻辑是对的（区分"概念没懂"和"题型不行"），但**同样依赖学生历史数据**。第一次做题的学生，走的是兜底逻辑（同章节随便推），你觉得"不准"是对的。
- **AI 出的题** —— 428 道，能用，但**离真题的水平还差一截**。真题的题干设计（怎么给条件、怎么埋坑）是几十年积累出来的，模型学不来。

## 1.2 这一轮我修的两个"要命"的 bug

**① 泄题（严重）**
`/api/questions` 这个接口，**把所有主观题的标准答案都发给了前端**。学生按 F12 就能看到答案。
这是从很早的版本就有的问题，一直没人发现。你要是拿去 demo，被人当场按 F12 打开，会很难看。
**已修**：题目列表现在一个答案字段都不发。

**② 学生数据串号（严重）**
`/api/answer` 里 `student_id` 是**写死的 `demo_student`**。也就是说，接入助学端之后，
**张三做的题会算到李四头上**。掌握度、推题、教师看板全乱。
**已修**：现在支持三种传法（body / URL 参数 / 请求头），并且验证过两个学生的数据是分开存的。

这两个 bug 都不是"质量问题"，是**接入之前必须修的硬伤**。修完了。

## 1.3 我没解决的

**① AI 出题的质量天花板**
我改了 4 版 Prompt，计算题从"只给一个数字"改到"完整解题过程 + 采分点"。
但**模型出的题，本质上是在"复述知识点"，不是在"设计一道题"**。
真题里那种"给你三个方案 (b)(c)(d)，让你算哪个能满足要求"的设计感，模型出不来。
**这个我认为靠 Prompt 解决不了**（下面第三节会说该怎么办）。

**② 真题的计算题只救回来 8 道**
剩下的要么原卷没答案，要么公式丢得太彻底。
我用"截图"绕过了这个问题（把原卷整个拍下来给学生看），但这是**权宜之计**，
它的代价是：**这些题没法自动批改**（因为答案是图，模型读不了）。

**③ 自反馈（你问的那个）—— 我现在做不了，原因说清楚**
你说的"自反馈"，我理解是：**系统自己发现出的题不好，然后自己改进**。
要做这个，需要一个闭环：
```
出题 → 学生做 → 收集数据（正确率、区分度、用时） → 判断题好不好 → 反馈给出题环节
```
**卡在第三步：没有真实学生数据。**
- 一道题"好不好"的客观标准是：**区分度**（会的人做对、不会的人做错）。
- 算区分度需要**至少 20 个学生做过这道题**。
- 我们现在有 **0 个真实学生**。

所以现在能做的"自反馈"，只能是**模型自己审自己**（`review/auto_review.py` 已经在做了），
但这是**左手打右手**——模型判断不了自己出的题是不是"真的能区分学生水平"。

**结论：自反馈的框架我可以先搭好（数据表、接口都留出来），但要等真实学生数据才能真正跑起来。**
我建议把它写进 todolist，不要为了"有这个功能"而做个假的。

# 二、我们这套到底是什么技术？（你组长问的）

> **⚠️ v20 更新：RAG 已经做了。** 下面这一节写于 v19，当时 RAG 还没做。
> 现在可以改口了——**我们已经有 RAG 了**（`pipeline/rag.py`）。
> 具体做了什么、为什么这么做，见本文件最后的「v20 补充」。

## 2.1 先纠正一个说法：我们不是"纯提示词工程"

你猜的方向对，但不完全。**我们实际上是三件事的组合**：

```
① 结构化知识库（Knowledge Base）
   7 章 × 150+ 知识点，每个知识点有：正文、公式、关键概念、前置依赖
   ↓
② 检索 + 提示词工程（Retrieval + Prompt Engineering）  ← 主体
   出题时：从库里取出这个知识点的原文、公式、学生的历史误区
          → 塞进 Prompt → 调 DeepSeek → 拿到 JSON
   ↓
③ 校验闭环（Validation Loop）
   出完的题过两道关：
   - 程序质检（validators.py）：算式对不对？选项是不是只有一个对的？
   - 模型审核（auto_review.py）：让另一个模型再审一遍，不合格的驳回
```

**准确的说法是**：
> **基于结构化知识库的检索增强 + 提示词工程 + 双重校验闭环**
> （不是 Agent，不是微调，不是蒸馏）

**为什么不算 Agent**：Agent 的核心是**自主决策 + 多步规划 + 调工具**（比如"我先查这个，再算那个，不对再回去查"）。
我们是**固定流程**：取知识点 → 出题 → 校验 → 入库。没有自主决策。

**为什么不算 RAG（严格意义上）**：真正的 RAG 是**向量检索**（把文档切块、做 embedding、按语义相似度召回）。
我们是**结构化查询**（`SELECT * FROM knowledge_points WHERE knowledge_id=?`）——按 ID 精确取，不是按语义搜。
**但从效果上，它起的是 RAG 的作用**（把外部知识注入 Prompt，防止模型胡编）。

## 2.2 那能不能用别的方法？会不会更好？

我查了业界的共识（2026 年的资料），**答案很明确**：

> **正确的顺序是：Prompt → RAG → Fine-tune → Distill**
> **"绝大多数团队不应该微调。他们应该先修好 Prompt、建好 RAG、写好评测。"**

具体到我们：

| 方法 | 值不值得做 | 我的判断 |
|---|---|---|
| **提示词工程**（现在在做） | ✅ 已经做了 | 这是**必须先做好**的地基。我改了 4 版 Prompt，计算题答案质量翻了几倍——**这个收益是实打实的** |
| **真 RAG（向量检索）** | ✅ **值得做，收益明确** | 见下 ⭐ |
| **微调（LoRA/SFT）** | ⚠️ **现在不值得** | 见下 |
| **蒸馏** | ❌ 完全不需要 | 蒸馏是为了把大模型压缩成小模型（省成本）。我们连成本问题都还没有 |
| **Agent** | ⚠️ 看怎么定义 | 见下 |

### ⭐ RAG：这个真的值得做，而且比赛大纲明确提到了

**比赛大纲第 5 页写着**：
> **（3）检索增强生成（RAG）**：深度接入对应学科的教材讲义、核心期刊论文、行业技术标准…
> 通过 RAG 技术**解决大模型幻觉问题**，确保生成内容的专业性、准确性与时效性。

**我们现在的做法的局限**：
出题时，我只把**这一个知识点**的原文喂给模型。
但真实的题目常常**跨知识点**（比如一道尺寸链计算题，同时用到"工艺基准"+"尺寸链"+"公差"三个知识点）。
**现在的做法出不了这种题**——因为模型只看到了一个知识点。

**上了 RAG 之后能做什么**：
- 出题时，按语义**召回相关的多个知识点**（不只是当前这一个）
- 把**真题原文**也纳入检索库 → 模型能"参考真题的出题风格"
- 出完题之后，**反查知识库验证**：这道题的答案在教材里有依据吗？（防幻觉）

**这是我认为最值得做的一个升级，而且工作量不大**（几百行代码 + 一个向量库）。

### ⚠️ 微调：现在别做，原因是数据量

微调需要**大量高质量的"标准答案"样本**（业界经验：至少几千条）。
我们有多少？**982 道题，其中真题只有 136 道。**
**用 982 条数据去微调，只会让模型学会"复读这 982 道题"，不会让它学会"出好题"。**

而且业界的共识很明确：**"微调是用来定型（form）的，不是用来灌知识（facts）的。"**
我们缺的是**知识的准确性**（这是 RAG 解决的），不是**输出格式**（这个 Prompt 已经解决了）。

**如果一定要微调**：得先攒够数据。等真实学生用起来、老师标注了一批"好题/坏题"之后，
可以用 **LoRA** 做一个轻量微调（业界说这是唯一现实的路径）。**但那是明年的事。**

### ⚠️ Agent：可以做，但要想清楚做来干嘛

如果把"出题"做成 Agent，它应该长这样：
```
Agent 收到任务："给第三章出 5 道计算题"
  → 自己决定：先查这一章有哪些公式
  → 自己决定：这个知识点没公式，跳过，换下一个
  → 出完题，自己调用"验算工具"检查算式
  → 算错了，自己重出
  → 还不行，自己去查教材原文，看是不是理解错了
```
**这个有价值**（尤其"自己验算、算错了自己重出"这一步）。
**但我们现在的固定流程 + 校验闭环，已经覆盖了 80% 的价值**（校验不过就驳回）。
**剩下 20% 是"自己修正"**——这个可以加，但优先级低于 RAG。

## 2.3 我给你组长的一句话回答

> **我们现在是"结构化知识库 + 提示词工程 + 双重校验闭环"，不是纯提示词工程。**
>
> **下一步最该做的是 RAG**（比赛大纲明确提到，能解决"跨知识点出题"和"防幻觉"两个真问题）。
>
> **微调现在不该做**——我们只有 982 条数据，微调只会让模型复读这些题。业界共识是
> "Prompt → RAG → Fine-tune"，我们连 RAG 都还没上，跳到微调是本末倒置。
>
> **质量优先的话，顺序应该是：RAG > Agent 化的自我修正 > 微调。**

# 四、关于你和我的交互方式（你问的）

## 4.1 你的表达方式：非常好，别改

我说真的。你的反馈有三个特点，**这三点让我的工作效率高了好几倍**：

1. **你会截图/贴出具体的错误现象** —— 比如你贴出"标准答案：可列出尺寸链如图 / 图中，为封闭环"，
   我一眼就能定位到是公式被吞了。**如果你只说"计算题答案不对"，我得猜半天。**

2. **你会追问"为什么一直没改好"** —— 这个特别重要。
   你逼我去找根因，我才发现问题在**我自己写的 Prompt 里**（`"answer": "最终数值答案"`）。
   **如果你只是重复"再改改"，我会继续在表层打补丁。**

3. **你会说"实在解决不了就告诉我"** —— 这给了我说实话的空间。
   否则我可能会硬做一个假的功能糊弄过去。

**唯一可以优化的**：有时候你一次给的东西太多（比如一次 10 条反馈 + 3 个文件），
我会**抓大放小**，可能漏掉其中一两条。你这次骂我"没看 prompt"就是这个原因——
**我确实漏了**（你说了组会结束、PDF 已发，我还在生成组会报告）。这是我的问题，不是你的。

**建议**：如果一次的反馈超过 5 条，**把"最重要的 1~2 条"单独标出来**（比如加个 ⭐）。
我会优先保证那几条不出错。

## 4.2 要不要先让 DeepSeek/GPT 给你生成 prompt，再来找我？

**跟我：不需要。而且会更糟。**

原因：
1. **我需要的是"现象"，不是"指令"。** 你说"计算题答案里出现了题干"，这是**现象**，我能定位根因。
   如果 DeepSeek 帮你翻译成"请优化计算题答案生成逻辑，确保题干与答案分离"，
   **这是个指令，但它丢失了最关键的信息**——到底哪道题、错成什么样。
2. **中间加一层 AI，会丢信息。** 你的原话里有很多"无意义"的细节（"我很生气"、"你怎么回事"），
   但这些恰恰告诉我**这个问题有多严重、你被卡了多久**。这些信息对我判断优先级很有用。

**跟 Codex/GPT 改代码：需要，而且很重要。**

区别在哪？**上下文。**
- 跟我，我们有几十轮的历史，我知道这个项目的每一行代码是怎么来的、为什么这么写。
- 跟 Codex，**它每次都是从零开始**。它不知道"为什么这里要用截图而不是文字"，
  它会自作主张给你改回去。

**所以给 Codex 的 Prompt，本质是"补上下文"。** 我给你一个模板：

### 给 Codex 的 Prompt 模板

```
# 项目背景
这是一个大学课程（机械制造工艺学）的智能题库系统。
技术栈：Python + SQLite + 原生 HTML/JS（无框架）。
所有数据在 db/question_bank.db 这一个文件里。

# 这次要改什么
[一句话说清楚，比如："给学生端加一个错题本功能"]

# 相关文件
- demo/serve_quiz.py     ← HTTP 服务，所有 API 在这
- demo/quiz_page.html    ← 学生端页面（HTML+CSS+JS 都在一个文件里）
- feedback/feedback.py   ← 批改逻辑
- db/question_bank.db    ← 数据库

# 必须遵守的约束（⚠️ 这几条不能违反）
1. **题目列表接口（/api/questions）绝对不能返回答案字段**（answer/explanation/answer_image）。
   学生按 F12 就能看到，这是泄题。答案只能从 /api/answer 返回。
2. **usage_scope='教师出题' 的题不能给学生**（这些题没有标准答案）。
3. **review_status != '已通过' 的题不能给学生**。
4. **所有涉及学生数据的接口，必须用请求里传的 student_id**，不能写死 demo_student。
5. 改完之后跑 `python pipeline/check_web.py`，必须全绿才算完成。

# 我的要求
- 改动要小、要精准。不要重构不相关的代码。
- 每改一个文件，告诉我改了哪几行、为什么。
- 如果你觉得我的需求有问题，直接说，不要闷头做。
```

**关键是那个"必须遵守的约束"部分。** 这是我们踩过的坑，**Codex 不知道，它会重新踩一遍**。
（比如它很可能会"好心"地把答案加回 `/api/questions`，因为那样"前端更方便"。）

## 4.3 什么时候需要"先生成 Prompt"这个流程？

一句话：**当对方 AI 缺少上下文的时候。**

| 场景 | 要不要先生成 Prompt |
|---|---|
| 跟我（有长期上下文） | ❌ 不需要，直接说现象 |
| 跟 Codex 改代码（每次从零开始） | ✅ 需要，要补项目背景和约束 |
| 跟 GPT 问通用知识（"什么是 IRT？"） | ❌ 不需要 |
| 让 AI 做一个复杂的、多步骤的任务 | ✅ 需要，要把步骤拆清楚 |

# 五、你要用 Codex 在 VSCode 里改代码，我的建议

**这个方式是对的**（尤其对你这种非技术背景的人）。但有几个坑：

## 5.1 ⚠️ 最大的风险：Codex 会"好心办坏事"

它看到 `/api/questions` 不返回答案，可能会想："这不合理，前端拿不到答案怎么显示？"

**对策**：把上面那个 Prompt 模板里的"必须遵守的约束"**每次都贴给它**。
或者更好：**在项目根目录放一个 `AGENTS.md` 文件**（Codex 会自动读），把约束写进去。
我已经帮你把这个文件生成好了（见压缩包里的 `AGENTS.md`）。

## 5.2 每次改完，跑一遍自检

```bash
python pipeline/check_web.py
```
这个脚本会检查：页面能不能打开、所有接口通不通、**有没有把没答案的题泄漏给学生**。
**全绿才算改完。** 这是我给你留的最后一道防线。

## 5.3 用 git

如果还没用，**现在就开始**：

# 八、v20 补充：RAG 做完了

你说"优先加 RAG"，我做完了。说清楚做了什么、为什么这么做。

## 8.1 做了什么

**① 检索引擎**（`pipeline/rag.py`）
把三个库做成了索引（1034 篇文档）：
- **知识点库**（283 条）→ 出题时提供教材原文
- **范例题库**（503 条：真题 + 教材原题）→ ⭐ 让模型学**真题的出题手法**
- **误区库**（248 条）→ 做干扰项

**② 出题时先检索**
以前：只把**这一个知识点**喂给模型 → 模型只能出单知识点的题，而且是"复述教材"。

现在：出题前先检索，把这些一起塞进 Prompt：
```
【相关知识点】（可以综合运用，出跨知识点的题）
· 装配尺寸链与工艺尺寸链的区别（第六章）：...
· 直线尺寸链的极值法计算公式（第二章）：A₀=∑增−∑减; T₀=∑Tᵢ
· 装配尺寸链的概念与构成（第六章）：...

【范例题】⭐ 老师真实出过的题，学它的**出题手法**（不要抄题，要学风格）
· [真题·名词解释·4分] 尺寸链
  参考答案：由多个尺寸首尾相连组成的封闭的圈。
· [教材习题·单选·2分] （判断）直线尺寸链中必须有增环和减环。

【学生的常见误区】（做干扰项用）
· 混淆了两种尺寸链的涉及对象和封闭环定义...
```

**注意上面那个例子**：出的是**第二章**的题，但检索把**第六章**的装配尺寸链也召回来了。
**这就是跨知识点出题** —— 模型现在能出"对比工艺尺寸链和装配尺寸链"这种有深度的题了，
以前它根本看不到第六章的内容。

**③ RAG 防幻觉**（比赛大纲第 5 页明确要求的）
出完题之后，**把「题干+答案」拿回去反查知识库**：
- 搜得到高度相关的知识点 → 有教材依据 ✅
- 什么都搜不到 → 模型可能在编 ⚠️ 标记出来让人看一眼

实测：真实概念相似度 0.217（通过），我编的"区块链哈希共识"相似度 0.072（被标记）。

**④ 错题本**（`/api/wrong_book`）
学生做错的题按知识点归堆。**最有价值的不是"我错了几道"，而是"我哪个概念反复错"**。
重做对了会自动移出错题本。

## 8.2 技术选型：为什么用 TF-IDF 而不是向量模型？（面试可能会问）

**先说结论：这是个有意识的权衡，不是偷懒。**

**原因1：DeepSeek 根本没有 embedding 接口。**
我查了官方 GitHub，明确写着 "No Embedding Support"。
要用向量，得再接一个模型（OpenAI/通义/本地 BGE）——**多一个依赖、多一份钱、多一个故障点**。

**原因2：我们的场景，TF-IDF 反而更合适。**
- 语料非常专业（"封闭环""增环""基准重合"）
- **专业术语的字面匹配 = 语义匹配**——"尺寸链"这三个字出现了，就是在讲尺寸链
- 语料量小（1034 篇），不需要复杂的近似检索
- 通用向量模型反而可能把"基准"理解成日常语义的 benchmark，**不如字面匹配准**

**原因3：中文分词的坑，我用字符 n-gram 绕过去了。**
中文没空格，标准 TF-IDF 要先分词（jieba）。我用 **2~3 字的字符 n-gram**：
"尺寸链" → ["尺寸", "寸链", "尺寸链"]。这样"工序尺寸链"和"尺寸链"能匹配上，**不依赖分词器**。

**换成真向量很容易**：只要实现 `embed(texts) -> vectors`，替换掉 `TfidfVectorizer`。
**其它代码（出题、Prompt 拼装）完全不用改。** 我在 `rag.py` 里标了 `EMBEDDING_ADAPTER` 注释。

## 8.3 面试怎么说这一段

如果面试官问"你们的 RAG 是怎么做的"：

> **真题范例**（让模型学真题的出题手法，而不是复述教材）、**学生误区**（做干扰项）。
